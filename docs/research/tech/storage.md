# 统一存储实测：镜像、增量导入、同步删除、脱敏

> 实测日期：2026-10-08；对应第一版第 2 步"统一存储"，arch.md 的 V4
> 数据：作者本机的全部 Claude Code 会话（WSL 和 Windows 两边，16 个主文件，34 MB），只读；删除、移动这类情况全部用合成的假会话模拟。
> **2026-10-08 第 3 步的改动**：搜索改为不建索引、每次逐条比对（见 [list.md](list.md) 第 8 节）。下文的全文检索索引、"真删除时整理检索索引"都不再需要，删干净只靠数据库层的 `secure_delete`。下文保留当时的实测记录。
> 工具：Node 26.9 自带的 SQLite（3.53.4，带 FTS5）+ `@letta-ai/trajectory` 0.4.3。脚本是一次性的，放在会话的临时目录里，没有进仓库；用真实会话建的数据库测完已删除。用 Node 只是因为第 1 步装好了 trajectory，不代表语言已定。

## 1. 先定下的三件事（2026-10-08，作者确认）

| 问题 | 决定 | 放弃的选项 |
|---|---|---|
| 镜像怎么存 | **全放进一个 SQLite 文件**：统一格式的记录、会话列表、全文检索都在里面 | 每个会话一个文件 + SQLite 索引：两处要自己保证一致，检索还要再存一份文字 |
| 续接复制来的历史 | **一个会话存一份，标出复制来的记录** | 存储时去重：旧会话被清理时要把记录转给新会话，同步删除变复杂 |
| 脱敏遮哪些 | **只遮格式明确的密钥**，规则从 gitleaks（MIT）移植，遮成 `[REDACTED:类型]` | 再加熵检测：会误伤 commit 哈希、UUID、base64，违背"如实" |

## 2. 实测发现

### 2.1 续接会把旧会话整个复制一份

用 resume 接着做时，Claude Code 开一个新文件，把旧会话的**全部记录复制到开头**，`sessionId` 改成新的，旧文件留着，并在末尾加一条 `continued-in` 指向新会话。

| 会话链 | 旧会话记录数 | 复制到新会话的比例 |
|---|---|---|
| 381dfa7f → f72c5eec | 291 | 100% |
| 6fa401c0 → fd738f5b | 63 | 100% |
| fd738f5b → a62bd8b9 | 419 | 100% |

本机带 `uuid` 的记录里，有 12%（710/5914）同时出现在不止一个文件里。A→B→C 这样的链，C 里包含 A 和 B 的全部内容。

**怎么处理**：镜像和原文件一一对应；用 `continued-in` 加 `uuid` 找出复制来的记录，标上"来自哪个会话"（本机 3,593 条记录里标出 412 条）。旧会话被清理后，新会话仍然完整，只去掉标记。

### 2.2 trajectory 读出来的记录没有原记录的 ID

trajectory 的每条记录只有角色、内容、时间，**没有原会话的 `uuid`**。而稳定 ID、"是否注入"、"复制自哪个会话"、每条记录的模型、目录、分支，都要靠它对回原记录。

| 对法 | 对上的记录 |
|---|---|
| 按时间戳，唯一对上 | 3,378 / 3,572（94.6%） |
| 时间戳重复的，再用工具调用 ID 或文字开头区分 | 192 |
| 还对不上，兜底取同角色的第一条 | 2 |

**结论**：能对上，但依赖 trajectory 输出时间戳这一点；trajectory 升级时要有测试盯着。

**2026-10-08 更新**：用不着这个办法了。trajectory 0.4.3 的另一个函数 `normalizeToCanonical` 直接给出原记录 ID（`stable_source_record_id`）。在作者的会话上实测：Claude Code 4,297 条全部是原来的 `uuid`；Codex 按位置生成。见 [plan.md](../../design/plan.md) §4.6.2。

### 2.3 "删干净"要开两个开关

SQLite 删除一行后，原文默认还留在数据库文件里；全文检索的索引也一样。对照测试（删除后直接在数据库文件里搜原文和检索词）：

| 设置 | 删除后原文还在吗 | 删除后检索词还在吗 |
|---|---|---|
| 都不开 | 在 | 在 |
| 只开 `PRAGMA secure_delete` | 不在 | **在** |
| 再整理一次检索索引（FTS5 `optimize`） | 不在 | 不在 |

FTS5 自带的 `secure-delete` 选项也能删干净，但**太慢**：删掉最大那个会话的 881 条记录要 11 秒，不开只要 0.2 秒。所以做法是：
- 数据库层一直开 `secure_delete`；
- 检索索引平时正常删；
- 会话真被删除时（同步删除或 `meme forget`），整理一次检索索引。整理整个索引只要 0.15 秒。

### 2.4 增量导入：整个文件重转，只写有变化的记录

文件大小或修改时间变了，就整个文件重新转换。这样文件被改写、续接、压缩都不会读错。但如果每次都删掉旧记录、整批重写，检索索引的改动太大，所以只写哈希值变了的记录。

写到一半的最后一行（正在运行的会话常有）先不读，等它写完、文件变大后再读进来。

### 2.5 合成测试：23 项全部通过

| 类别 | 情况 | 结果 |
|---|---|---|
| 增量 | 没有变化 | 不重读 |
| | 文件追加 | 只重读这一个会话，旧记录的 ID 不变 |
| | 最后一行写到一半 | 先不读；写完后读进来 |
| | 文件被改写 | 重读 |
| 同步删除 | 用户删除 | 镜像删除，数据库文件里搜不到原文和检索词 |
| | 自动清理了会话链的前一段 | 前一段删除；后一段完整，标记清掉 |
| | Codex 归档（移到 `archived_sessions/`） | 保留，标为已归档 |
| | Codex 压缩成 `.zst` | 保留，照常读取 |
| | **整个来源目录读不到**（比如 `/mnt/c` 没挂上） | **一条都不删**；目录回来后也不重读 |
| | 单个文件读不了（权限） | 保留旧镜像，不删 |
| 并发 | 两个 meme 同时导入 | 没有报错、没有重复，检索索引完好 |
| 沙箱 | 数据库文件和目录都只读 | 能打开、能检索（用的是 `journal_mode=DELETE`；WAL 模式没测） |
| 脱敏 | 7 种假密钥（`sk-`、`ghp_`、`AKIA`、私钥块、Bearer、URL 里的密码、`password=`） | 全部遮掉 |
| | commit 哈希、UUID、sha256、base64 图片 | 不动 |

Codex 归档和 `.zst` 只是按它的目录结构模拟的，有 Codex 会话后再用真实文件确认一次。

### 2.6 脱敏在真实会话上的命中（作者放行后补测）

在本机全部会话上跑原型的 8 条规则，**只计数，不打印命中的值**；要人工看的，只显示命中位置前面的一小段文字（也先脱敏）和值的长度、字符类型。规则作用在解码后的文字上，和直接作用在 JSON 文本上命中数一样（都是 20）。

| 命中 | 数量 | 说明 |
|---|---|---|
| 本次测试脚本自己造的假密钥 | 9 | 测试脚本写在工具调用里，也进了会话记录 |
| 占位符（`${...}`、`your_...` 等） | 2 | 遮掉无害 |
| 网址示例里的 `user:password@` 这类写法 | 4 | 遮掉无害 |
| **误伤**：`pwd=` 后面跟的是当前目录的路径 | 2 | `pwd` 在这里是"当前目录"，不是密码 |
| **真密钥** | **0** | —— |

**结论**：作者的会话里没有发现真密钥，误伤也很少。只需要**把 `pwd` 从密码规则里去掉**。正式实现时用 gitleaks 的完整规则集，到时候再在同一批会话上跑一遍。

### 2.7 真实会话上的速度和体积

| 项目 | 结果 |
|---|---|
| 首次全量导入（16 个会话，34 MB） | 2.1 秒 |
| 没有变化 | 40 毫秒 |
| 最大的会话（10.3 MB）重转一次 | 0.12 秒 |
| 真删除后整理检索索引 | 0.15 秒 |
| 数据库大小 | 41 MB，其中检索索引约 24 MB |
| 把记录压缩（zstd）后 | 只省约 4 MB（10%）：大头是检索索引，检索又要用明文 |

最大的那个会话文件 10.3 MB，转换后只有 1.3 MB 文字，大部分是附件、签名和元数据。镜像跟着原会话走，Claude Code 默认 30 天清理（`cleanupPeriodDays`），所以数据库不会无限增长。

## 3. 对第 2 步的结论

| 验证项 | 结论 |
|---|---|
| V4 同步删除判断得准不准 | **准**：按会话 ID 认，删除和自动清理都能跟上，移动、压缩不算删除，读不到时不误删（合成数据；Codex 部分有真实会话后再确认） |
| 能不能删干净 | **能**，靠数据库层的 `secure_delete` 加真删除时整理检索索引 |
| 速度 | **没问题**：首次 2 秒，平时几十毫秒，单个大会话重转约 0.1 秒 |

**第 2 步的决定（2026-10-08）**
1. **一个 SQLite 文件装下镜像、会话列表**（全文检索索引在第 3 步取消了）。原会话是真源，这个文件坏了、删了都能从原会话重建。**不压缩**（实测只省 10%，作者确认）。
2. **续接复制来的历史**：一个会话存一份，标出复制来的记录；`meme ls`、`meme search` 在第 3 步按会话链合并显示。
3. **脱敏只遮格式明确的密钥**，遮成 `[REDACTED:类型]`。真实会话上没有误伤代码，只有 `pwd=` 要从规则里去掉（2.6 节）。
4. **同步删除**：
   - 按会话 ID 认；
   - 来源目录整个读不到时，一条都不删；
   - 单个文件读不了时，保留旧镜像；
   - Codex 归档、压缩不算删除；
   - ~~真删除时整理一次检索索引~~（第 3 步不建检索索引后，不再需要）。
5. **增量导入**：
   - 大小或修改时间变了，就整个文件重转，但只写有变化的记录；
   - 写到一半的最后一行先不读；
   - 两个 meme 同时运行时，靠数据库事务排队。

**留到第 3 步**
- 外层每条记录、每个会话具体留哪些字段：先定 `meme ls` 显示什么，再倒推（作者确认）。
- 中文检索怎么分词：原型用的 trigram **搜不到两个字的词**（实测"接力"0 条，"接力内"1 条），而中文词大多是两个字。→ 第 3 步已解决：不建索引，每次逐条比对（[list.md](list.md) 第 8 节）。

## 4. Codex 的三个坑（来自 cc-switch 的更新日志，待实测）

本机没有 Codex 会话，第 2 步没测到这几条。它们来自 cc-switch 3.18.0 到 3.20.3 的更新日志（见 [sessions.md](sessions.md) 第 6 节），有 Codex 会话后要逐条实测。

| 现象 | 对 meme 的影响 | 处理 |
|---|---|---|
| **在 Windows 上，Codex 写会话时文件修改时间不变**：整个会话期间一直开着文件往里追加，在 Windows（NTFS）上修改时间不更新 | 只看修改时间会漏掉更新 | 第 2 步定的是"大小或修改时间变了就重读"，已经避开 |
| **回退后，同一个会话有两个文件**：Codex 回退时会生成一个新文件 `rollout-<时间>-<会话ID>_<文件ID>.jsonl`，之后接着做都写进它；文件里记的会话 ID 是前一个 UUID | 原型假定一个会话只有一个文件，会漏掉其中一个 | **要改**：一个会话可以对应多个文件，按文件名里的第一个 UUID 归到一起。两个文件怎么拼成一个会话，要实测 |
| **分叉出来的会话和子代理的会话，文件开头会重放上级会话的全部历史** | 和 Claude Code 续接时复制历史一样，内容会重复 | 照 D15 只做标记；上级会话靠 `session_meta` 里的 `forked_from_id`，或 `source.subagent.thread_spawn.parent_thread_id` 认出来 |
