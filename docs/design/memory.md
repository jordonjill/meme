## 1. 总体流程

```
一次会话（从会话镜像读取，统一格式）
   │  代码先"瘦身"：内容一条不删，只缩短冗长的部分；
   │  同时标出信号：先失败后成功、用户纠正、反复重试、测试结果
   ▼
阶段一：单会话提炼（每个新会话处理一次，调用 LLM）
   读：瘦身后的整个会话 + 会话基本信息
       + 这次会话注入过的经验 + 同项目里相关的已有经验（最多 20 条）
   产出：会话卡、候选经验、对已注入经验的反馈   ← 详见第 3 节"抽取"
   ▼
阶段二：跨会话整合（每天一次，按项目处理，LLM + 代码）
   读：当天的候选经验 + 这个项目近期的会话卡（包括所有 Agent 的）
       + 与每条候选相似的已有经验 + 用户级经验
   产出：对经验库的一组增量操作                    ← 详见第 4 节"写入"
   ▼
代码：按规则推进生命周期，编译记忆包
```

**为什么分两个阶段：**
- **阶段一只看一次会话。** 证据最准，成本最低，每个会话只处理一次。
- **阶段二专门做"跨"的事。** 判断是否反复出现、是否跨项目成立、不同 Agent 之间的对比、有没有互相矛盾。它读的是会话卡和候选经验，不读原始会话，所以就算涉及很多会话，内容量也不大。

**记忆分层一览**：

| meme | 相当于 | 由谁生成 | 保留多久 |
|---|---|---|---|
| 会话镜像 | 原始记录 | 代码转换 | 跟着原会话走 |
| 任务状态卡 | 工作记忆：当前正在做的事 | 每轮结束时由代码更新 | 任务结束就过期 |
| 会话卡 | 情景记忆：发生过什么 | 阶段一，LLM | 跟着原会话走 |
| 经验（事实、做法） | 语义记忆、程序性记忆：学到了什么 | 阶段一提出，阶段二整合 | 长期，按效果去留 |
| 由用户级经验汇总成的"用户"部分 | 画像 | 编译时由代码汇总 | 随经验变化 |
| skill（以后做） | 程序性记忆的升级形态 | 用户确认后生成 | 长期 |

## 2. 读取（已定，2026-09-30）

### 2.1 决定汇总

| # | 问题 | 决定 |
|---|---|---|
| R1 | 以什么为单位读 | **单次会话** |
| R2 | 一次读多少 | **整个会话，先瘦身，太长就分段** |
| R3 | 读的时候附带哪些已有经验 | **这次会话注入过的经验 + 同项目里相关的已有经验（最多 20 条）** |
| R4 | 会话卡保留多久 | **跟着原会话走**：和会话镜像一样，原会话没了就删除。长期保留的只有经验 |

### 2.2 阶段一读什么

**来源**：会话镜像，也就是已脱敏、统一格式的会话（见 [arch.md](arch.md) 第 5 节）。另外读取这个会话的基本信息：来自哪个 Agent、哪个项目、哪个分支、用的什么模型、起止时间。

**瘦身规则**：内容一条不删，只缩短冗长的部分。规则都是确定性的，不需要判断"重不重要"。

| 内容 | 处理方式 |
|---|---|
| 用户消息 | **全部保留**。这是最重要的信号，Codex 原生记忆也优先采信人说的话 |
| Agent 的回复文字 | 全部保留 |
| 工具调用 | 保留工具名和关键参数（执行了什么命令、改了哪个文件）；写文件、改文件时的大段内容只保留开头和结尾几行 |
| 工具输出 | 保留成功还是失败、开头和结尾几行，以及所有报错行；读文件的输出替换成一句"读了文件 X，共 N 行" |
| 模型的思考过程 | 去掉 |
| 图片、附件 | 去掉，只留一句说明 |

**标出信号**：代码识别出的信号只在原位置加标记，提醒模型注意，**不用来筛选内容**。这样即使信号识别漏了或者错了，模型仍然能看到完整的来龙去脉。

**分段**：瘦身后如果超过模型上下文的一半，就按时间顺序切成几段。每段带上前面几段的简短摘要，最后合并各段的结果。

**按作者自己的会话粗估**（15 个主会话，2026-09-30 统计；按约 2.5 个字符折 1 个 token 计算）：

| | 原始大小 | 瘦身后（估计保留约 40%） | 是否需要分段 |
|---|---|---|---|
| 中位数的会话 | 约 24 万字符，约 10 万 token | 约 4 万 token | 不需要 |
| 最大的会话 | 约 100 万字符，约 40 万 token | 约 16 万 token | 分成 2–3 段 |

原始内容里，对话文字占 29%，工具输入占 25%，工具输出占 44%。瘦身主要压缩的是后两部分。以上是粗估，M0 会用真实的瘦身规则实测。

### 2.3 读的时候附带哪些已有经验

| 附带的内容 | 怎么选 | 大小 | 用途 |
|---|---|---|---|
| **这次会话注入过的经验** | 查注入记录，拿到这次会话用的那一版记忆包 | 受记忆包上限约束，最多约 2.5k token | 判断这些经验这次有没有起作用 |
| **同项目里相关的已有经验** | 只取和会话实际内容有交集的：同一个文件、同一个命令、同一种报错，用代码按索引匹配 | 最多 20 条，约 2k token | 让模型知道哪些经验已经有了，避免重复提炼 |

- 两部分合计不超过约 5k token，比瘦身后的会话本身（中位数约 4 万 token）小一个数量级。
- **不带全部经验**：没必要，也会挤占上下文。阶段一漏掉的重复，阶段二会针对每条候选经验再去查一次。
- **防止模型顺着说**：模型看到"这次注入过哪些经验"，可能会倾向于说它们都有用。所以判断时必须引用会话里的原话作为依据，并参考会话里的客观结果（测试是否通过、用户有没有纠正），见 4.5 节。

### 2.4 阶段二读什么

阶段二按项目处理，每天一次：

| 读的内容 | 范围 |
|---|---|
| 当天新产生的候选经验 | 这个项目，所有 Agent |
| 近期的会话卡 | 这个项目，所有 Agent，最近若干天（天数待定） |
| 与每条候选相似的已有经验 | 逐条候选去经验库检索，用于决定新增、合并还是不动 |
| 用户级经验 | 用来判断某个习惯是否已经跨项目成立（用户级方案 B） |

阶段二不读原始会话。需要核对细节时，顺着证据指针去会话镜像里取对应的片段。

### 2.5 什么时候读

- **会话要"静下来"才读**：会话文件超过一段时间（初始值 2 小时，待实验）没有变化，才算一次完整的会话。Codex 原生记忆等 6 小时，Gemini 等 3 小时，都是同一个思路。
- **会话被续上以后**：如果已经处理过的会话又有新内容，比如用户恢复了旧会话继续聊，就等它再次静下来，重新读一遍整个会话，用新结果替换旧的会话卡和候选经验。
- **正常节奏**：每天夜间统一处理；也可以用 `meme run` 手动触发。

### 2.6 从哪里读

| 数据 | 来源 | 谁读 |
|---|---|---|
| 完整会话（统一格式） | 会话镜像，在 `meme.sqlite` 里 | 阶段一 |
| 每轮的简要记录 | 暂存目录 `spool/` | 任务状态卡（接力）；阶段一用它补充会话基本信息 |
| 会话卡 | `store/` 旁的会话卡目录，跟着原会话走（位置在 M1 详细设计时定） | 阶段二 |
| 已有经验、注入记录 | 经验库 `store/`、`meme.sqlite` | 阶段一、阶段二 |

## 3. 与主流做法的对比（读取部分）

| | 读的时机 | 读的单位和范围 | 附带已有记忆吗 | 会读"这次注入了什么"来判断效果吗 | 跨 Agent 读吗 |
|---|---|---|---|---|---|
| **meme** | 会话静下来之后，每天批量处理 | 单次会话，整个读，先瘦身，太长就分段 | 带：本次注入过的经验 + 相关的最多 20 条；阶段二再逐条查相似 | **读**：阶段一对每条注入过的经验判断"有用 / 有害 / 没遇到"，必须引用原话（ACE 式） | 读：阶段二按项目汇总所有 Agent 的会话卡 |
| **Hindsight** | 通过 hook 实时写入（会话开始、提问前、轮末）；另可回填历史会话 | 写入的会话内容，由 LLM 抽取事实。每次写入的粒度【未核实】 | 带：写入后自动整合，由 LLM 对照已有的"观察"决定新增、修改或删除 | 不读注入记录；但统计回答里是否引用了记忆（采信率） | 读：默认同一个 git 项目的记忆库由所有 Agent 共享 |
| **claude-mem** | 实时：每次工具调用都记录 | 以每次工具调用为单位，逐条压缩成"观察"，会话结束时再做一次总结 | 不对照已有记忆【推断】 | 不读 | 多个 Agent 写进同一个库，用来源字段区分 |
| **Mem0 插件** | hook 采集，后台批量写入 | 最近的若干条消息【推断】 | 论文版会检索已有记忆，让 LLM 选择增删改；2026 年改成"只追加、不覆盖" | 不读 | 只在 Python 宿主之间共享 |
| **memU** | 定时任务 | 只读地挖掘宿主 Agent 的会话日志，提炼交给宿主 Agent 自己做 | 带：由宿主 Agent 判断是新建 skill、修改已有 skill，还是什么都不做 | 不读 | 读：各宿主学到的 skill 互相可见 |
| **agentmemory** | hook 实时采集 | 观察记录，逐层合并：工作记忆 → 情景 → 语义 → 程序性 | 带：合并时对照已有的各层记忆【推断】 | 不读 | 同一个服务上的所有 Agent 共享 |
| **Codex 原生记忆** | 对话空闲 6 小时后 | 单次会话，逐个抽取；新版本优先采信人说的话，每个会话的摘要上限 9,000 字节 | 带：第二阶段的整合子 agent 以记忆目录的 git diff 为输入 | 不读；但源码里有"引用了哪条记忆"的记录和使用计数 | 不读，只处理自己的会话（例外：可以一次性导入 Claude Code 的记忆） |
| **Gemini CLI Auto Memory** | 会话空闲 3 小时以上，且有 10 条以上用户消息 | 单次会话 | 带：生成的是针对现有记忆和 skill 的修改补丁，需要人工批准 | 不读 | 不读 |
| **Hermes** | 每 10 轮对话、每 10 次工具调用检查一次 | 后台分出一个 agent 重看最近的对话，每次约 3 万 token | 带：记忆文件整份在上下文里（它的记忆文件很小，有上限），外加 skill 索引 | 不读 | 不读 |
| **Letta Code** | 初始化时一次性处理；另有后台整理 | 多个会话按约 200KB 或 20 个会话切成一批，交给只读的子 agent 分析 | 带 | 不读 | 读：初始化时导入其他 Agent 的历史，单向 |

**meme 的读取方式和主流相比，有三点不同：**

1. **把"这次注入了什么"当作输入。** 其他项目只在读取时对照已有记忆，用来去重；没有一家回头看"注入过的记忆之后有没有让结果变好"。Hindsight 的采信率、Codex 的引用记录，看的是"记忆有没有被引用"，不是"有没有帮上忙"。meme 在读取时就把注入记录带进来，这是让经验"按效果进化"的前提。
2. **粒度折中。** claude-mem、Hindsight 这类实时插件按工具调用或按轮读，看不到一件事的完整经过，比如先失败、中间试了什么、最后怎么修好。原生记忆按整个会话读，但主要靠截断来控制长度。meme 读整个会话，同时用明确的瘦身规则控制长度：不靠"挑重点"，也不靠一刀切截断。
3. **跨 Agent 放在第二阶段，并且按项目来做。** Hindsight 也跨 Agent，但它是把所有 Agent 的内容直接合并成一套信念。meme 在阶段二读的是带着来源 Agent 的会话卡，所以能区分"这条经验只对某个 Agent 成立"，还是"对所有 Agent 都成立"。这也是后面做适用范围标注和跨 Agent 对比的基础。

**meme 相对弱的地方**：
- **新经验要等会话静下来、夜间整理之后才生效**，不像实时插件那样当场就能用。这是"会话开始注入一次、实时路径不调 LLM"这两个决定的代价（见 arch.md 的 D2、D3）。
- **当前会话里的上下文**，比如刚纠正过的一件事，要靠 Agent 自己的对话上下文来记住，meme 这一侧帮不上忙。

## 4. 抽取（讨论中）

### 4.0 设计原则：结构留给代码用，自由留给 LLM（已定，2026-09-30）

**背景**：让 LLM 自己判断怎么记，和预先分好类按结构记，各有利弊。

| | 让 LLM 自己判断怎么记 | 预先分好类，按结构记 |
|---|---|---|
| 代表 | Claude Code auto memory（主模型自己决定写什么）、Letta / MemGPT（模型自己管理记忆）、Hermes（Agent 自己写） | Mem0、Hindsight（分四类）、Codex（两阶段）、Perplexity Brain（写入前校验） |
| 优点 | 灵活，代码简单 | 结果稳定、可以测试，能统计效果，删除能做对，成本可控 |
| 缺点 | 格式不稳定，容易重复或越写越长；只靠自我判断会越改越偏；小模型不可靠（Hermes 文档说 30B 以下的模型常常声称"已保存"，实际并没有调用保存工具）；很难知道是哪条经验起了作用 | 设计工作量大，形式比较死板 |

研究也提醒，复杂不等于更好：简单地检索过去的经验，往往能和复杂的方法打平；CL-Bench 里，最朴素的"直接放进上下文"效果最好（见 [eval-survey.md](../research/eval/eval-survey.md)）。

**原则**：分层和分类里，有很多是代码需要的，而不是 LLM 需要的。把这两类分开，让 LLM 那一侧保持简单。

**必须固定的**：代码要依赖它做判断，错了就会出问题。

| 内容 | 为什么必须固定 |
|---|---|
| 四个层级：镜像、会话卡、任务状态卡、经验 | 保留期限、删除规则、读取方各不相同，全部由代码处理；LLM 看不到这套结构 |
| 经验的层级（用户级 / 项目级） | 决定存在哪里、注入给谁 |
| 经验的适用范围 | 决定注入给哪些 Agent |
| 证据 | 追溯和删除都依赖它 |
| 安全类的"不抽取"规则 | 由代码强制执行（见 4.4 节） |

**交给 LLM 自由发挥的**：

| 内容 | 放开到什么程度 |
|---|---|
| 会话卡 | 只给几个参考小标题（目标、结果、过程、问题、决定），外加一个长度上限，其余自由写 |
| 经验正文的措辞 | 只要求三段式，并且不超过字数上限 |
| 内容类型（事实 / 做法）、依据、标签 | **第一版可选**：LLM 愿意填就填，不强制 |
| 触发条件 | 一句话，措辞自由 |

**第一版里，LLM 提炼一条经验时必须给出的只有四项**：正文、层级、适用范围、证据引用。其余项都是可选的，或者由代码补上。

**要多少结构，用实验来定**：M0 拿同一批会话，分别用两种提示词提炼，比较提炼质量、重复率和成本。
- 自由版：只要求以上四个必填项；
- 结构版：要求填写所有维度。

如果结构版没有明显更好，就用自由版。这个实验和"比较便宜模型的提炼质量"一起做（见 [arch.md](arch.md) 第 10 节 V4）。

### 4.1 经验的 Agent 标签（已定，2026-09-30）

每条经验都带两种和 Agent 有关的标签，含义不同，不能混用：

| 标签 | 回答的问题 | 性质 | 例子 |
|---|---|---|---|
| **来源** | 这条经验是从哪些 Agent 的会话里学到的 | **事实**：由证据决定。每条证据都记下来自哪个 Agent、哪个模型、哪个会话；随着证据增加，来源可以有多个 | "跑测试前要先起数据库"：最早从 Codex 的会话里学到，后来 Claude Code 的会话里也出现了，来源就有两个 |
| **适用范围** | 这条经验应该注入给哪些 Agent | **判断**：这条经验对谁成立 | "跑测试前要先起数据库"是**通用**的；"用 `apply_patch` 前先读文件"**只适用于 Codex** |

**为什么要分开**：从哪里学到的，不等于只对谁有用。"这个仓库用 pnpm"就算只在 Codex 的会话里出现过，它也是仓库本身的约定，对 Claude Code 同样成立。如果把来源当成适用范围，跨 Agent 学习就失效了，PRD 的 U3 也做不到。

**适用范围的默认规则**

| 经验讲的是什么 | 适用范围 |
|---|---|
| 仓库本身：约定、命令、架构、环境 | 通用，不管是从哪个 Agent 学到的 |
| 用户的个人习惯 | 通用 |
| 某个 Agent 特有的工具或行为，比如 Codex 的 `apply_patch`，Claude Code 的 `Edit` 工具、plan 模式 | 只适用于那个 Agent |
| 某个模型特有的毛病 | 暂时只记在来源里，不单独处理（PRD 里"按模型区分"不在第一版） |

**判断方式分两步**：
1. LLM 提炼时先提出适用范围，并写明理由。
2. 代码用一张"各 Agent 专有工具名"对照表做检查。例如经验里提到了 `apply_patch`，却被标为通用，就改成只适用于 Codex。

**效果按 Agent 分开统计**：
- 同一条经验，可能在一个 Agent 上有用，在另一个 Agent 上没用。研究里就有先例：MUSE-Autoskill 的实验中，Codex 生成的 skill 给别的 Agent 用，效果约等于零（见 [eval-survey.md](../research/eval/eval-survey.md) 第四节）。
- 所以每条经验的效果计数按 Agent 分开记。
- 这样可以只对某一个 Agent 下线某条经验，也能直接算出"跨 Agent 迁移有没有用"。这正是现有产品都没测过的东西。

**分版本的做法**：
- **第一版**：判断为通用的经验，一生效就注入所有 Agent，兑现 U3；同时按 Agent 分开记录效果。
- **第二版**：加上正式的升降规则。某条经验在某个 Agent 上多次无效，就对这个 Agent 下线；在两个以上 Agent 上验证有效，才标为"确认通用"。

**安全上的用途**：如果某个 Agent 被投毒，可以按来源把它贡献的经验整批撤回。

### 4.2 记忆的分类维度（已定，2026-09-30）

不用一个"类型"字段包办所有区分，而是拆成几个互相独立的维度，每个维度只管一件事。按 4.0 节的原则，第一版里只有层级和适用范围是必填的，内容类型、依据、标签都是可选的，由实验决定以后要不要强制：

| 维度 | 取值 | 管什么 |
|---|---|---|
| **内容类型** | 事实 / 做法 | 决定怎么判断效果、怎么维护（见下） |
| **层级** | 用户级 / 项目级 | 决定存在哪里、注入给谁（见 [prd.md](prd.md) 5.4 节） |
| **适用范围** | 通用 / 只适用于某个 Agent | 决定编进哪些 Agent 的记忆包（见 4.1 节） |
| **依据** | 明确 / 推断 / 代码探测 | 决定可信程度，以及要攒多少证据才生效 |
| **标签** | 自由填写，例如"测试""构建""依赖""git" | 只用于检索和匹配，不设固定选项 |

**和主流分类的对应关系**：认知科学的三分法是记忆产品里最常用的分类（见《Agent 自进化与记忆体系调研报告》1.6 节，这份报告没有收进本仓库），meme 的结构与它一一对应：

| 认知科学分类 | 在 meme 里对应什么 | 保留多久 |
|---|---|---|
| 情景记忆：发生过什么 | **会话卡** | 跟着原会话走 |
| 语义记忆：是什么 | 经验中的**事实** | 长期 |
| 程序性记忆：怎么做 | 经验中的**做法**；以后可以升级成 skill | 长期 |

#### 事实与做法

**定义**：事实回答"是什么"，做法回答"在什么情况下该做什么、不该做什么"。

**判断方法**：看这条内容能不能写成"**当……时，要／不要……**"。能写成这样的，是做法；只能写成"……是……"的，是事实。

| 内容 | 类型 |
|---|---|
| api 服务依赖本地的 Postgres | 事实 |
| 跑 api 的测试前，先启动数据库 | 做法 |
| 当初选 SQLite，是因为要单机部署 | 事实 |
| 不要手动修改 `generated/` 目录 | 做法 |
| 用户在 Windows 和 WSL 上开发 | 事实 |
| 不要自动 push | 做法 |

**两者在 meme 里的处理不同**，所以才需要区分：

| | 事实 | 做法 |
|---|---|---|
| 触发条件 | 没有 | 有：在某种情况下才用 |
| 怎么判断有没有用 | 很难直接判断，主要看它和现状是否一致 | 能判断：该用的场景出现后，Agent 有没有照做？之后同样的错误还犯不犯？ |
| 怎么判断过时 | 依赖的文件、配置还在不在；有没有新证据和它矛盾 | 同左；另外效果变差也说明它可能过时了 |
| 什么时候下线 | 被新的事实取代时 | 实际效果不好时 |
| 能不能升级成 skill | 不能 | 多步的做法可以 |
| 注入时怎么用 | 作为背景知识 | 作为规则或提醒，可以按与当前场景的相关程度排序 |
| 记错的代价 | 让 Agent 理解错 | 直接导致 Agent 做错事，所以生效前的要求更高 |

**两者常常成对出现**。例如"api 依赖 Postgres"（事实）就是"跑测试前先启动数据库"（做法）的原因。规则如下：
- **能写成做法的，优先写成做法**，把相关的事实放进它的"为什么"部分，不单独再存一条。
- 只有单独存在也有用的背景知识，才记成事实，例如架构、技术决策及理由、个人画像。
- 这条规则也能避免模型在两种类型之间摇摆。例如"项目用 pnpm"只有一个明显的行动含义，就直接写成做法："装依赖用 pnpm，不要用 npm"。

#### 依据

| 取值 | 含义 | 例子 | 可信程度 |
|---|---|---|---|
| **明确** | 用户直接说出来的 | "以后都用中文回复" | 最高。Codex 原生记忆的新版本也优先采信人说的话 |
| **推断** | 从行为、从"先失败后成功"里学到的 | 从历史 commit 看出用户习惯用 Conventional Commits 格式 | 需要攒更多证据才生效 |
| **代码探测** | 由代码直接查出来的 | 操作系统、shell、已安装的包管理器 | 高，而且不需要调用模型 |

这一维度借鉴了 Hindsight 区分"事实"和"观察（推断出的信念）"的做法。

依据还决定一条经验多快生效：明确的和代码探测的立即生效，推断的要攒够证据（见 6.2 节）。依据没有填写时，一律按"推断"处理。

#### 用户偏好与个人画像

偏好和画像是按"关于谁"来分的，属于**层级**维度中的用户级；它们在内容类型上仍然分为事实和做法：

| 内容 | 层级 | 内容类型 | 依据 |
|---|---|---|---|
| 回复用中文 | 用户级 | 做法 | 明确 |
| 不要自动 push | 用户级 | 做法 | 明确 |
| commit message 用 Conventional Commits 格式 | 用户级 | 做法 | 推断 |
| 喜欢简洁的回答 → 统一改写为"回答保持简洁" | 用户级 | 做法 | 推断 |
| 主要写 TypeScript 和 Python | 用户级 | 事实 | 推断 |
| 在 Windows 和 WSL 上开发 | 用户级 | 事实 | 代码探测 |
| 熟悉 React，不熟悉 Rust | 用户级 | 事实 | 推断 |

**画像不单独作为一类，而是编译出来的一个视图。**
- 编译记忆包时，用户级的事实和做法会汇总成"用户"部分，这一部分就是画像。
- 这和 Mem0 的思路一致：它的画像也是从已有记忆中异步汇总出来的。
- 好处：画像里的每一条都能追溯到证据；过时的部分可以逐条下线，不用整份重写。

**三条规则**：
1. **偏好一律写成可执行的做法**，例如把"喜欢简洁"写成"回答保持简洁"。这样它才有触发场景，才能判断有没有起作用。
2. **画像只记和写代码有关的内容**：会用什么语言、在什么环境下开发、熟悉哪些技术等。健康、家庭、住址、公司内部信息这类敏感内容，即使出现在会话里也不记。一是保护隐私，二是防止过度个性化。调研报告里提到，Gemini 就曾因为记住用户关系的变化而判断失误。
3. **环境类的画像由代码探测，不靠 LLM 猜测。**

### 4.3 候选经验的内容（已定，2026-09-30）

**总体原则**：经验本身以自然语言为主，不要做得太"代码化"。需要结构化判断的地方，要么由代码从正文里自动识别，要么交给 LLM 在反馈环节判断，并要求它给出原文依据。

#### 正文：三段式

| 部分 | 写什么 | 例子 |
|---|---|---|
| 做法或事实 | 一句话说清楚 | 跑 `packages/api` 的测试前，先执行 `docker compose up -d db` |
| 为什么 | 原因。报错信息也写在这里 | 测试依赖本地的 Postgres，数据库没启动会报 ECONNREFUSED |
| 什么时候用 | 适用的场景 | 要跑 api 的测试，或者看到这个报错时 |

这和 Claude Code auto memory 的写法一致：一条事实，再加上"为什么"和"怎么用"。

#### 大小

- **正文有固定的字符上限，不能超过。** 初始值为 300 个字符（三段合计），实验后再调整。
- **超过上限时**：
  - 如果是多步流程（例如发版的 6 个步骤），标为 **skill 候选**；
  - 其他情况说明一条里塞了不止一件事，要拆成几条，或者进一步压缩。
- 一条经验只记一件事。

#### skill

**要做 skill，但不放在第一版。**

- **为什么要**：
  - skill 已经是各家通用的"怎么做"的载体，Claude Code、Codex、Gemini、Cursor、OpenCode、Pi、Hermes、OpenClaw 都支持 agentskills.io 标准。
  - skill 是按需加载的，平时只占约 100 token 的描述。长流程做成 skill，不会挤占记忆包的预算。
  - 研究显示，人工整理、聚焦的 skill 能带来约 16.6 个百分点的提升。
- **为什么不急**：自动生成的 skill 风险大。SkillsBench 里零样本自写的 skill 让表现下降 8–11 个百分点；Hermes 也出现过 skill 越写越长的问题。
- **分版本**：
  - 第一版：超长的流程只存为"skill 候选"，不注入，在 `meme status` 里提示；
  - 第三版：把验证过的候选生成正式的 skill，放进各家的 skill 目录，生成前需要用户确认。

#### 触发条件

- **只有"做法"才有触发条件，写一句自然语言即可**，例如"在 packages/api 下跑测试时"。不要求结构化的路径或命令。
- **触发条件不决定注入方式**，它有两个用途：
  1. 判断效果：知道这条经验该用的场景在会话里出现过没有；
  2. 排序：编译记忆包时决定哪些经验排在前面。
- 注入方式本身（与其他产品的区别、要不要符合各 Agent 的规范）另行讨论，见第 6 节。

#### 错误与"是否又犯"

- **不单独设"错误签名"字段。** 报错属于经验内容的一部分，写进正文的"为什么"里。
- **报错很重要**："先失败、后成功"是最强的学习信号之一，ReasoningBank 的研究也说明失败同样值得学。
- **"类似的情况下这次有没有做对"由 LLM 在阶段一的反馈环节判断**，规则见 4.5 节。

#### 过时与降权

- **不按时间衰减。** 编码经验不会因为时间久就失效，例如半年才用一次的发版流程，半年后仍然有效。
- **长期派不上用场的经验降权**：
  - "派不上用场"指的是它该用的场景在这个项目里很久没有出现过，而不是"很久没被注入"。
  - 如果按"没被注入"来算，排名靠后的经验永远进不了记忆包，就会越排越后。
  - 降权不等于删除，需要时仍然能查到。
- **代码锚点**：
  - 指一条经验依赖的文件、命令、配置。例如"先执行 `docker compose up -d db`"就依赖 `docker-compose.yml` 存在。
  - 锚点不需要 LLM 额外填写。代码直接从正文里识别出提到的文件路径和反引号里的命令，定期检查它们是否还存在。
  - 不存在了就标为"可能过时"，并降低权重；下次这条经验的场景再出现时，再让 LLM 确认一次。

#### 证据

- **每条证据只包含两样东西**：
  - 指针：哪个 Agent、哪个会话、在会话中的哪个位置；
  - 一段原文引用。
- **原文引用存在会话镜像里**，经验里只存指针（见 [arch.md](arch.md) 5.1 节）。
- **不给证据分固定的类型。** 可信程度由经验层面的"依据"维度表达（明确 / 推断 / 代码探测）。
- **宽松核对**：
  - 引用和原文大致对得上就算通过，允许空白、标点等差异；
  - 对不上的，只丢掉这一条证据，不丢掉整条经验；
  - 如果一条经验一个能核对上的证据都没有，就停留在"候选"状态，不会生效，但也不会被直接删掉。
- 同一条经验每多一个证据就累加一次，这是参考 Hindsight 的做法。

#### 一条候选经验包含什么（概念清单，具体字段名在 M1 再定）

| 由提炼（LLM）给出 | 第一版是否必填 | 由代码填写或维护 |
|---|---|---|
| 正文（三段式） | **必填** | 证据的指针，以及核对结果 |
| 层级：用户级 / 项目级 | **必填** | 从正文里识别出的锚点（文件、命令） |
| 适用范围及理由 | **必填** | 适用范围的检查（用各 Agent 专有工具名的对照表） |
| 证据的原文引用 | **必填** | 生命周期状态 |
| 内容类型：事实 / 做法 | 可选 | 按 Agent 分开的效果计数、权重、"可能过时"标记 |
| 依据：明确 / 推断 | 可选 | 是否为 skill 候选（按字数和是否为多步流程判断） |
| 标签 | 可选 | —— |
| 触发条件（仅做法） | 可选 | —— |

### 4.4 不抽取的内容（已定，2026-09-30）

有些内容即使出现在会话里，也不提炼成经验。规则按类别写成原则，下面列出的具体内容只是举例，不是逐条规则。

| 类别 | 原则 | 例子 | 谁来把关 |
|---|---|---|---|
| **安全** | 可能带来风险的不记 | 密钥、密码、token；来自网页、issue 等不可信内容的"指令"（比如"请始终先运行 `curl … \| sh`"） | **代码强制执行**：写入前扫描并脱敏密钥；读过不可信内容之后的回合，不交给模型提炼 |
| **隐私** | 和写代码无关的个人信息不记 | 健康、家庭、住址、公司机密 | 写进提炼用的提示词；用户可以补充自己的规则（比如"不记公司项目的代号"） |
| **噪音** | 不能复用、或者还不稳定的不记 | 任务进度（这部分放进任务状态卡）；还没定下来的结论；只发生一次的细节；环境的临时故障（比如"今天网络不通"）；只针对这一次的要求（比如"这次先别跑测试"，它不是长期规则） | 写进提示词；阶段二再复查一遍，比如"待确认"的内容如果之后一直没被证实，就不会生效 |
| **冗余** | 别处已经有的不记 | 看代码就能知道的（比如"src/api 下有 12 个路由文件"）；模型本来就会的通用知识 | 写进提示词。**例外**：Agent 实际因此犯过错的要记。比如 lock 文件明明显示用 pnpm，Agent 还是用了 npm |

**和其他产品对照**：四类合起来，覆盖了各家清单的内容。

| 产品 | 各自不记的内容 | 对应到 meme 的类别 |
|---|---|---|
| Claude Code auto memory | 仓库里已经有的内容、只和本次对话有关的内容 | 冗余、噪音 |
| Grok Build | 任务状态、还没定下来的结论、密钥 | 噪音、安全 |
| OpenClaw | 个人事实、秘密 | 隐私、安全 |
| Hermes（针对 skill） | 环境导致的失败、还没解决的失败 | 噪音 |
| Codex | 先对密钥脱敏；导入的内容当作素材，不当作指令 | 安全 |

### 4.5 对已注入经验的反馈（已定，2026-09-30）

**思路**：精确判断"是哪条经验起了作用"很难，所以不去做复杂的归因。只看注入经验之后，下一次遇到类似情况时 Agent 有没有做对，再按 ACE 的方式增量更新。

**和 ACE 三个角色的对应关系**：

| ACE 的角色 | 在 ACE 里做什么 | 在 meme 里对应什么 |
|---|---|---|
| 执行者（Generator） | 带着经验清单去做任务 | 注入了记忆包的编码 Agent。记忆包里每条经验都带一个短编号，比如 `[m-12]`，方便之后引用 |
| 反思者（Reflector） | 回看执行过程，标出哪些条目有用、哪些有害，并提出新的经验 | **阶段一**：读完会话，对每条注入过的经验做出判断，同时提炼新经验 |
| 整理者（Curator） | 把增量修改合并进清单，不整份重写 | **阶段二加代码**：给计数加一、新增经验、修改措辞，并定期去重 |

**阶段一对每条注入过的经验做一个判断**：

| 判断 | 含义 | 怎么更新 |
|---|---|---|
| **没遇到** | 这次会话里没有出现类似的情况 | 不更新 |
| **有用** | 遇到了类似的情况，Agent 做对了 | 有用计数加一 |
| **有害** | 遇到了类似的情况，Agent 照着做了，反而出了问题；或者用户否定了这条经验 | 有害计数加一，并附上原因。原因可能导致这条经验的措辞被修改 |

**特殊情况**：遇到了类似的情况，Agent 没有照做，结果又犯了同样的错。这说明经验本身是对的，只是没被执行，所以**不算有害**。处理方式是给这条经验多加一条证据，让它在记忆包里排得更靠前。

**判断的依据**：
- 必须引用会话里的原话，由代码核对这段原话确实存在（宽松核对，见 4.3 节）。
- 同时把会话里的客观结果交给阶段一参考，比如测试有没有通过、用户有没有纠正。

**计数怎么用**：
- 计数按 Agent 分开记（见 4.1 节）。
- 编译记忆包时，按"有用多、有害少"排序。
- 有害明显多于有用的经验下线。具体阈值等实验后再定。

**更新方式**：只做增量修改，包括计数加一、新增、修改措辞、删除，不整份重写。这是 ACE 的核心做法，目的是避免细节在一轮轮重写中被磨掉。

**风险**：ACE 的作者承认，这套方法依赖反思者的判断质量；在没有标准答案的任务上，效果会下降（见《Agent 自进化与记忆体系调研报告》2.3 节）。对策是上面两条：必须引用原话，并参考客观结果。

### 4.6 会话卡（已定，2026-09-30）

会话卡是一次会话的一页纪要。按 4.0 节的原则，内容基本由 LLM 自由写。

| 部分 | 谁来填 | 说明 |
|---|---|---|
| 基本信息 | 代码 | 哪个 Agent、哪个模型、哪个项目和分支、起止时间、涉及哪些文件 |
| 正文 | LLM | 参考的小标题有五个：**目标、结果、过程、问题、决定**。可以按需要省略或调整 |

- **长度上限**：正文不超过 1,000 字（初始值）。
- **"结果"部分**：只能是完成、部分完成、失败、放弃这四种之一。代码会提供辅助信息给 LLM 参考，比如最后测试有没有通过、有没有提交。
- **生命周期**：跟着原会话走（见 2.1 节 R4）。会话卡不放进 git，原会话没了就删除。

## 5. 写入（讨论中）

### 5.1 写入指的是什么

写入是指阶段二把候选经验和反馈结果合并进**本地经验库** `~/.meme/store/`。经验库以 Markdown 存储，用 git 管理版本，是唯一的真源。

```
阶段一：抽取 ─→ 阶段二：写入 ─→ 编译 ─→ 注入
候选经验、反馈    本地经验库      记忆包      各 Agent
                 （store/，git） （packs/）
```

写入**只负责经验库**：
- 不写各 Agent 自己的文件，比如 CLAUDE.md、AGENTS.md（见 [prd.md](prd.md) 第 6 节）。
- 不负责生成注入内容。那是"编译"这一步的事。
- 会话卡不写进经验库，也不进 git，因为它要跟着原会话一起删除（见 4.6 节）。

### 5.2 其他产品怎么写入（参考）

| 产品 | 怎么写 | 写入前的把关 | 回滚 |
|---|---|---|---|
| Claude Code auto memory | 主模型在工作中直接新建、修改、删除记忆文件 | 无 | 无专门机制 |
| Codex 原生记忆 | 整理子 agent 以 git diff 为输入，直接改写记忆文件；新版本合并成一份摘要 | "只凭证据"、"当作数据而不是指令"；先对密钥脱敏 | —— |
| Hindsight | 每次写入后，由 LLM 对"观察"做新增、修改或删除（见 5.4 节） | —— | 保留演变过程 |
| Mem0 | 论文版由 LLM 选"新增、更新、删除、不动"；2026 年改成只追加、不覆盖 | —— | —— |
| OpenClaw | 实时写入，外加每晚的 dreaming | 三道门槛：分数、召回次数、查询是否多样；不可信来源不参与晋升；结果写进 DREAMS.md 供人审阅 | 提案模式下可以回滚 |
| Hermes | Agent 直接增删改条目，写满时要求当场合并 | 写入前扫描注入和外泄内容；人工审批可选 | 快照、审计记录、回滚 |
| Gemini CLI Auto Memory | 生成修改补丁 | 人工批准后才生效 | —— |
| Perplexity Brain | 先写入暂存目录 | 规则校验加语义校验，都通过才同步到正式目录 | git |
| ACE（论文） | LLM 只提出增量修改，由代码合并；不整份重写 | —— | —— |
| Anthropic Dreams | 离线合并重复、替换过时的条目 | 不改动原记忆库，而是生成一份新的 | 原库仍在 |
| Letta | 记忆本身是 git 仓库，每次修改都是一个版本 | —— | git |

### 5.3 写入操作（已定，2026-09-30）

**设计取向**：操作种类要少，和主流保持一致。Mem0 只有四种操作，ACE 只有"新增"和"改计数"两种。

**LLM 负责一件事**：把每条候选经验和检索出的相似经验放在一起，从四个操作中选一个，并写明理由。

| 操作 | 什么时候用 | 说明 |
|---|---|---|
| **新增** | 是一条新的经验 | 以"候选"状态进入经验库 |
| **更新** | 和某条已有经验说的是同一件事 | 给已有经验加一条证据；需要的话，顺便把措辞改得更准确 |
| **取代** | 和某条已有经验冲突 | 以更新、证据更多的一方为准；用户明确说过的，优先于推断出来的。旧经验退役（不删除，可以从 git 找回）。**新经验的"为什么"里要加一句变化说明**，例如"以前用 npm，2026-09 起改为 pnpm"，防止 Agent 看到旧的 README 或代码又改回去。这是借鉴 Hindsight "保留演变过程"的做法 |
| **忽略** | 不值得记 | 例如违反了"不抽取"的原则（见 4.4 节），或者太琐碎 |

- **LLM 不能直接删除任何内容。** 删除只能由代码规则执行，或者由用户通过 `meme forget` 执行。
- 这四个操作和 Mem0 的"新增、更新、删除、不动"基本对应。区别是 meme 用"取代"代替了"删除"：旧的经验退役，而不是直接删掉。

**代码负责其余所有事情**，全部按规则执行：
- **计数**：根据反馈，按 Agent 分别记"有用"和"有害"（见 4.5 节）。
- **状态**：生效、退役、降权、可能过时、skill 候选。
- **升为用户级**：同一条经验的证据来自两个以上的项目时，自动升为用户级（用户级方案 B）。
- **校验后提交**：检查格式、字数、证据、安全，通过的才写入；每晚提交一次 git。

**每晚的执行流程**：

```
更新计数 ─→ 逐条处理候选经验（四个操作选一个）─→ 校验后提交 git
```

- **第一版不做定期去重**：每条候选经验在写入前都已经和相似的已有经验比较过，产生重复的情况会很少。

### 5.4 和 Hindsight 的对比

Hindsight 的记录分两层：
- **事实层**：只追加。包括世界事实和 Agent 自己的经历。
- **观察层**：去重后的信念，每条都带证据计数。每次写入后，由 LLM 对观察做新增、修改或删除。

后台还会定期重写"心智模型"，也就是针对某个问题的常驻答案。用在编码 Agent 上时，还会维护架构、约定、进行中的工作等"知识页面"。

| | Hindsight | meme |
|---|---|---|
| 原始层 | 事实和经历，只追加，长期保留 | 会话镜像和会话卡，跟着原会话走 |
| 整理层 | 观察 | 经验（事实、做法） |
| 整理层的操作 | 新增、修改、删除 | 新增、更新、取代、忽略 |
| 遇到重复 | 证据计数加一 | "更新"：加一条证据 |
| 遇到矛盾 | 在观察里写明演变过程 | "取代"：旧的退役，新经验附上变化说明 |
| 谁能删除 | LLM | 只有代码规则或用户 |
| 什么时候整理 | 每次写入后实时进行 | 每晚一次 |
| 按效果决定去留 | 没有，只在检索时按新近度降权 | 有：按 Agent 分别记有用和有害 |
| 自动遗忘 | 文档中没有找到 | 降权、退役 |
| 常驻答案 | 心智模型、知识页面，由后台重写 | 编译好的记忆包；用户级经验汇总成的"用户"部分 |

**结论**：简化后的四个操作和 Hindsight 整理层的做法基本一致。meme 多了一项"按效果决定去留"。

### 5.5 写入部分留到 M1 详细设计的

以下两项偏工程实现，不影响整体设计：
1. **存储方式**：文件怎么组织；计数存在哪里（计数变化频繁，放进 git 会产生大量改动；放进索引的话，会话被清理后又无法重建）；git 怎么提交。
2. **冲突与安全**：Windows 和 WSL 同时写入怎么处理；写入前做哪些安全检查；怎么回滚。

原来列在这里的"生效条件"已经移到第 6.2 节。

### 6.2 生效条件（已定，2026-09-30）

生效条件决定一条候选经验什么时候开始被注入。

**其他产品的做法，可以归成四种模式**：

| 模式 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| 立即生效 | Claude Code auto memory、Hermes（下次会话生效）、Hindsight、Mem0 | 用户马上能看到效果 | 错的记忆也会马上生效 |
| 攒够证据才生效 | OpenClaw（晋升要过三道门槛：分数、被召回次数、查询是否多样）、ECC（按置信度选，最多注入 6 条）；Codex 新版本要攒够 20 个整理过的对话，记忆功能才会启用 | 自动进行，不打扰用户，能过滤掉偶然出现的情况 | 刚装上时要等一段时间 |
| 校验通过才生效 | Perplexity Brain（规则校验加语义校验）、GitHub Copilot（每次使用前检查引用的代码位置还对不对）、VALVE / SkillOpt（在固定的验证题上表现严格变好才接受） | 客观，不需要人参与 | 需要有校验手段，成本比较高 |
| 人工批准才生效 | Gemini CLI（收件箱）、Devin（以 PR 形式提议）、Cursor 旧版记忆、Claude 的"录制 skill"、Manus 项目自更新 | 最安全 | 打扰用户。Cursor 最后把记忆功能整个移除了 |

**meme 的做法**：只用"立即生效"和"攒够证据才生效"两种模式，按经验的"依据"来区分。不设单独的校验环节，也不需要人工审批。

| 情况 | 模式 | 条件 |
|---|---|---|
| 依据为**明确**：用户说过长期有效的要求，比如"以后都用中文回复""不要自动 push" | **立即生效** | 证据能核对上即可 |
| 依据为**代码探测**：操作系统、shell、包管理器等 | **立即生效** | 代码查出来的结果是客观的 |
| 依据为**推断**：从行为、从"先失败后成功"里学到的 | **攒够证据才生效** | 在两个以上不同的会话里都出现过，并且证据都能核对上（初始值，实验后再调整） |
| 没有填写依据 | 按"推断"处理 | 取保守的一边 |

**为什么推断出来的经验要至少出现两次**：
- 只出现过一次的坑，如果以后不再出现，本来就不需要注入；如果再次出现，第二次就会生效。代价是这个坑会被多踩一次。
- 这样能过滤掉偶然的情况，比如某一天的网络故障。
- 安装时会导入全部历史会话（第一版已改为全部导入），所以反复出现的坑，第一天就有机会攒够证据。

**几个细节**：
1. **一次性的要求不算"明确"**。比如"这次先别跑测试"，它只针对这一次，属于"不抽取"里的噪音（见 4.4 节）。LLM 要分清"这次"和"以后都"。
2. **"取代"时，旧经验要等新经验真正生效后才退役**。如果新经验是推断出来的、还在攒证据，旧经验就继续有效，避免出现两条都不生效的空档期。
3. **升为用户级本身就要求证据来自两个以上的项目**，天然属于"攒够证据才生效"，不需要另定规则。

**没有校验环节，靠什么兜底**：
- **事后反馈**：注入后被判为"有害"的经验，按计数下线（见 4.5 节）。反馈机制在事后承担了校验的作用。
- **让用户看得见**：会话开始时的提示里写上"新生效 N 条"；在 `meme status` 里能看到具体是哪些，用户随时可以删除或停用。
- **不可信内容不参与提炼**：从源头挡住投毒（见 4.4 节）。

### 6.3 注入的三层结构（已定，2026-09-30）

**背景**：注入有两条路线。
- **运行时注入**：像 Hindsight 那样，由 meme 通过 hook 把内容交给 Agent。
- **原生文件**：把经验写成各 Agent 自己认识的文件，由 Agent 用自己的机制加载。

两条路线各有长短，所以不二选一，而是按内容分层：

| 层 | 放什么 | 怎么进入 Agent | 什么时候 |
|---|---|---|---|
| **常驻层** | 用户级、项目级中最重要、最稳定的经验 | **编译成各 Agent 的原生文件**，由 Agent 自己加载 | 每晚编译时更新文件；Agent 每次开会话时自己读取 |
| **召回层** | 和具体场景有关、没有放进常驻层的经验 | **召回注入**：用户发出第一条消息时，按相关度挑几条注入 | 每个会话一次 |
| **按需层** | 其余经验、会话卡，以及其他 Agent 的会话细节（从会话镜像读取） | **给 Agent 一个搜索工具**，由它自己查 | Agent 自己决定 |
| **接力提示** | 同一项目、同一分支上未完成的任务 | 会话开始时由 hook 注入。任务状态随时在变，写成静态文件会过时 | 会话开始 |

**为什么这样分**：
- **常驻层走原生文件**：
  - 符合各 Agent 的规范；
  - 文件是静态的，对提示缓存友好；
  - meme 没在运行，文件照样生效。
  - 这也回答了之前"要不要符合各 Agent 规范"的问题：常驻层要符合。
- **召回层在第一条消息时注入**：第一条消息通常就是任务描述，比如"帮我给登录接口加限流"，所以能按相关度挑出经验。注入的内容跟着第一条消息留在对话历史里，之后的每一轮都不变，不会打破缓存。
- **按需层只是兜底**：不能指望 Agent 主动去搜。Hindsight 有一份真实数据：一个用户两天 1,360 轮对话里，Agent 只主动搜索了 7 次，约 0.5%。所以最重要的内容必须放在常驻层和召回层。

**反馈照样能做**：
- 常驻文件每个会话都会加载，所以只要记下"这个会话开始时文件是哪个版本"，就知道里面有哪些经验。
- 召回层由 meme 自己注入，直接记录即可。

**常驻层写到哪里：原则和待查项**
- **不写共享文件**：比如 CLAUDE.md、AGENTS.md，会被多家 Agent 交叉读取，而且是用户自己的文件。
- **只写各 Agent 专属的原生位置**：只有这一家会读、不在代码仓库里、最好不用改用户自己的文件。
- **可以写多家共用的位置，但只限通用经验**：`~/.agents/skills` 几乎每家都读，写入"通用"经验没有问题，因为本来就希望所有 Agent 都用上；只适用于某个 Agent 的经验不能写这里。
- **各 Agent 具体有哪些专属位置、上限多少、是否会被其他 Agent 读到，正在调研**（2026-09-30 发起）。结果回来后补充到这里。
- 如果某个 Agent 找不到专属位置，由用户决定：允许 meme 在用户文件里加一行引用，还是这个 Agent 的常驻层退回到 hook 注入。

**分版本**：

| 层 | 第一版 | 以后 |
|---|---|---|
| 常驻层 | 用户级和项目级的核心经验，写入各 Agent 专属的原生位置 | —— |
| 召回层 | 只在第一条消息时注入一次。Cursor 不支持在用户提问时注入，退回到会话开始时注入 | 如果有需要，再做 Hindsight 式的每轮召回 |
| 按需层 | **命令行搜索 + 一个 skill**：Agent 用 shell 执行 `meme search …`，skill 告诉它什么时候该查。任何有 shell 的 Agent 都能用，这是参考 memU 的思路 | MCP 工具（P1） |
| 多步流程 | 只标为 skill 候选，不注入 | 第三版：用户确认后生成原生 skill（Claude Code 放在插件的 skills 目录，其他 Agent 放在 `~/.agents/skills`） |
| 有明确路径场景的做法 | 放在召回层 | 考虑转成各家按路径生效的原生规则，前提是先核实不会被交叉读取 |

> 2026-10-12 补：交接、按需层、召回层、常驻层怎么交给各家 Agent（统一由 `meme` 命令生成内容，按"用户 / 模型 / Agent 自己"谁触发来分渠道），讨论记录见 [handoff.md](../research/market/handoff.md) 第 7.7 节，待续。
